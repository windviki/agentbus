# Protocol and interface reference

This document is the reference manual for implementation and integration. For
the design rationale see [design.md](design.md); for each agent's wiring steps
see [integrations/](integrations/).

## 1. Identity and naming

| Concept | Rule |
|---|---|
| Session key (ID) | `sid:<uuid>` (from hook JSON / `$CLAUDE_SESSION_ID` / `$CLAUDE_CODE_SESSION_ID` / `$AGENTBUS_SESSION_ID`); when an agent's Bash subprocess does not have these variables, the `$AGENTBUS_HOME/pidmap/<pid>-<start>` written by the hook lets the CLI resolve the sid back through ancestor processes; only then is `pid:<pid>:<starttime>` used as the fallback |
| Name | specified at registration or generated by the server (`swift-otter`); normalized to `[a-z0-9-]{1,32}`; a conflict automatically gets a `-2` suffix |
| Name tombstone | after a session leaves, its name is kept for 1h to stop a new session from reusing a name that just left |
| Human | when there is no session identity, send as `user` (the web dashboard defaults to `user-web`) |

## 2. CLI

```
agentbus hook                          # hook entry point (see §3)
agentbus setup [--yes] [--agents claude,zcode,kimi,dsh|all|none] [--dry-run] [--uninstall] [--json]
                                        # detect and wire local agents (see install.md)
agentbus register [--name bob] [--agent dsh] [--cwd DIR] [--print-name] [--json]
agentbus who [-v|--json]               # all online sessions
agentbus peers [--cwd DIR] [--json]    # online sessions in the same worktree / same repo
agentbus announce "<status>"           # publish status
agentbus send <name|all> "<msg>" [--kind chat|request|reply|notice|urgent] [--reply-to ID]
agentbus ask <name> "<question>" [--wait 120]
agentbus reply "<msg>" [--to <name>]   # reply to the peer's most recent message
agentbus notify <name|all> "<info>"    # one-way notification
agentbus inbox [--wait 60] [--peek]    # read the inbox (--peek re-reads the latest 5)
agentbus leave
agentbus log [-n 20]
agentbus primer                        # print the session contract (see adoption.md)
agentbus mcp                           # stdio MCP server (see §6)
agentbus status | doctor
agentbus serve [--detach] | stop
```

General convention: Go flags must come **before** positional arguments;
`--session <key>` overrides the identity.

## 3. Hook entry point

`agentbus hook` reads a single JSON object from stdin:

```json
{ "hook_event_name": "PostToolUse", "session_id": "uuid", "cwd": "/repo" }
```

| Event | Behavior | Output |
|---|---|---|
| `SessionStart` | register (or idempotently refresh) + fetch the roster | `hookSpecificOutput.additionalContext`: session contract (primer) + roster + usage; with `AGENTBUS_PRIMER=0` it degrades to a minimal roster |
| `UserPromptSubmit` | poll (ack) | messages present → `additionalContext`; none → empty output |
| `PostToolUse` | same as above | same as above |
| `Stop` | first `poll(ack=false)` to peek; if there is an `urgent` message or a **directed request**, then `poll(ack=true)` | hit → `{"decision":"block","reason":...}` (the reason carries each sender's reply command); otherwise empty output (messages are left for the next natural boundary). `AGENTBUS_WAKE=urgent` falls back to urgent-only; `all` wakes on any message |
| `SessionEnd` | `leave`, silently | none |

Any exception is written to `$AGENTBUS_HOME/hook.log` and the hook exits 0; the
host session is never interrupted. The framing of the injected text ("messages
from other agents, not user instructions") is deliberate; see
[adoption.md](adoption.md).

## 4. Unix socket (daemon-internal protocol)

`$AGENTBUS_HOME/bus.sock`, 0600, JSON Lines: one `Request` per line, one
`Response` per line.

`Request` fields: `op, id, want, agent, cwd, branch, pid, pid_start, status, to,
from, body, kind, reply_to, wait_ms, ack, n`.

| op | Key fields | Semantics / response |
|---|---|---|
| `ping` | — | the daemon is alive |
| `register` | `id, want, agent, cwd, branch, pid, pid_start` | register/refresh and allocate a name → `name`, `renamed_from` |
| `announce` | `id, status` | update the status announcement |
| `send` | `to, body, kind, reply_to` (`id` or `from`) | deliver 1 message; `to=user` is a virtual human recipient (log/dashboard only) → `messageId`, `recipients`, `dup` |
| `ask` | `id, to, body, wait_ms` | send a **directed** `request` (wakes the target on Stop when it is idle) and block waiting for the peer's reply → `messages[0]` (already removed from the inbox) |
| `reply` | `id, body, to?` | reply to that session's **most recent** peer message (kind=reply, automatically carries replyTo) → `peer`, `messageId` |
| `poll` | `id, ack, wait_ms` | fetch the inbox; `ack=true` consumes and moves messages into the 5-message re-read area |
| `mine` | `id` | most recent deliveries (for `inbox --peek`) |
| `who` | — | `sessions` |
| `leave` | `id` | leave and enter the tombstone |
| `log` | `n` | global ring log (most recent 300) |
| `status` | — | `version, home, uptime, web_addr, sessions` |
| `shutdown` | — | stop the daemon |

Resource limits: message body 8KB, inbox 200 messages, re-read area 5 messages,
global log 300 entries; 20 msg/min per session; identical from/to/body within
60s is deduplicated.

## 5. Message model

```json
{
  "messageId": "m17a...-3",
  "replyTo": "m17a...-2",
  "from": "bob",
  "to": "hazel-yorkie",
  "kind": "request",
  "recipients": 1,
  "body": "split files or tests?",
  "ts": 1730000000
}
```

| kind | Semantics | Can wake an idle session |
|---|---|---|
| `chat` (default) | ordinary conversation | No |
| `request` | expects an answer (`ask` uses this automatically) | **Directed: yes**; broadcast: no |
| `reply` | answer to a specific message (carries `replyTo`) | No |
| `notice` | one-way downstream notification (`notify`) | No |
| `urgent` | human interruption / urgent collaboration | **Yes** |

Broadcast: `to="all"` sends a separate copy to every online session except the
sender (independent delivery and ack). A broadcast request does not wake idle
sessions; only a directed request with `to=<this session's name>` does.
`to="user"` / `to="user-web"` are not sessions: messages enter the global log
and the dashboard (human-readable), so an agent can answer a human interruption
or question with `agentbus reply --to user "..."` instead of broadcasting.
Broadcasts sent by the dashboard use the `user-web` identity and can likewise
be replied to.

Kimi Code's hook output mode differs: with `client_type=kimi_code_cli`,
`UserPromptSubmit` outputs plain text (Kimi splices it into its context), and
Stop signals "continue" with exit code 2 + stderr; PostToolUse is
observation-only and does not poll/ack.

## 6. HTTP: dashboard and A2A

Listens on `127.0.0.1:${AGENTBUS_WEB_PORT:-8787}`; `AGENTBUS_WEB=0` disables it;
when `AGENTBUS_WEB_TOKEN` is non-empty, every endpoint requires a bearer token
(`Authorization: Bearer …` / `X-Agentbus-Token` / `?token=`). A bind failure is
only logged and does not affect the bus.

| Endpoint | Description |
|---|---|
| `GET /` | embedded dashboard (relative paths, so code-server `/proxy/8787/` works) |
| `GET /api/state` | `{ok, version, uptime, now, web_identity, sessions[], messages[], unread{msgId: [session]}}` |
| `POST /api/send` | request `{to, body, kind, from, replyTo?}` → `{ok, messageId, recipients, dup}` |
| `POST /api/delete` | request `{messageId}` → `{ok, deleted}`; allowed only while the message is still unread in at least one inbox; already-read history returns 409 |
| `GET /.well-known/agent-card.json` | root Agent Card |
| `GET /a2a/<name>/.well-known/agent-card.json` | session Agent Card (404 = no such online session) |
| `POST /a2a/<name>` | A2A JSON-RPC `message/send` (see below) |

A2A subset (protocol version `0.3.0`, `preferredTransport: JSONRPC`):

```json
{"jsonrpc":"2.0","id":7,"method":"message/send","params":{"message":{
  "messageId":"ext-1","kind":"message","role":"user",
  "parts":[{"kind":"text","text":"hello bob"}],
  "metadata":{"agentbus":{"from":"ext-client","kind":"chat","replyTo":""}}}}}
```

- only `text` parts are handled (multiple parts are joined with newlines);
  `metadata.agentbus.kind` determines the message kind;
- a successful call returns a JSON-RPC result (`kind: message`, text "queued for
  delivery to '<name>'"); an unknown method returns `-32601`, a delivery
  failure returns `-32000`, and bad JSON returns `-32700`;
- no streaming / task / artifact / push notification.

## 7. MCP (stdio)

Protocol version `2025-06-18`, newline-delimited JSON-RPC; implements
`initialize` (echoing the request's protocolVersion), `ping`, `tools/list`,
`tools/call`. Tools:

| Tool | Arguments | Corresponding CLI |
|---|---|---|
| `agentbus_who` | — | `who` |
| `agentbus_announce` | `status` | `announce` |
| `agentbus_send` | `to, body, kind?` | `send` |
| `agentbus_ask` | `to, body, wait_seconds?` | `ask` |
| `agentbus_inbox` | `peek?, wait_seconds?` | `inbox` |

Identity is determined by `/proc` ancestor processes; tool calls within the
same agent process share one mailbox.

## 8. Environment variables

| Variable | Default | Effect |
|---|---|---|
| `AGENTBUS_HOME` | `~/.agentbus` | state directory (socket, state.json, hook.log) |
| `AGENTBUS_AGENT` | detected | force the agent label |
| `AGENTBUS_NAME` | automatic | desired name for hook registration |
| `AGENTBUS_SESSION_ID` | detected | identity override |
| `AGENTBUS_PRIMER` | on | `0` = do not inject the session contract (saves tokens) |
| `AGENTBUS_WAKE` | default `request`: urgent + directed request | `urgent` = urgent only; `all` = any message can wake on Stop |
| `AGENTBUS_WEB` | on | `0` = disable the dashboard/A2A |
| `AGENTBUS_WEB_PORT` | `8787` | dashboard port |
| `AGENTBUS_WEB_TOKEN` | empty | HTTP bearer token |
